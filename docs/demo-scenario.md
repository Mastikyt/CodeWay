# Сценарий демонстрации CodeWay (≈5 минут)

Цель: показать разницу между ролью **студент** (`role: "user"`) и **администратор** (`role: "admin"`): не только какие кнопки видны, но и как сервер сам проверяет права.

Демо-аккаунты (из `db.json`, кнопки быстрого входа на `/login`):

| Роль | Email | Пароль |
|---|---|---|
| Администратор | `admin@codeway.by` | `admin123` |
| Студент | `user@codeway.by` | `user123` |

---

## 0. Запуск (≈30 секунд)

Вариант для разработки — два окна терминала в корне проекта:

```bash
npm run api    # API + раздача dist на http://localhost:3001
npm run dev    # Vite на http://localhost:5173 (proxy /api → :3001)
```

Открыть **http://localhost:5173**.

Вариант без Vite — одна команда после сборки:

```bash
npm run build
npm run api
```

Открыть **http://localhost:3001** — сервер отдаёт собранный фронтенд и API с одного порта.

Что должно быть на экране: `npm run api` пишет «🚀 CodeWay API Сервер запущен на http://localhost:3001»; для варианта с `npm run dev` в Vite — «Local: http://localhost:5173». Порт `5173` фиксирован (`strictPort`), если он занят — Vite завершится с ошибкой; освободить порт `3001`: `Get-Process -Id (Get-NetTCPConnection -LocalPort 3001).OwningProcess | Stop-Process -Force`.

> Перед защитой желательно подставить постоянный `TOKEN_SECRET` (см. `.env.example`): без него сервер генерирует случайный ключ при старте, и после каждого перезапуска API нужно входить заново.

---

## 1. Вход студентом (≈30 секунд)

1. Открыть `/login` (ссылка «Войти» в шапке).
2. Внизу карточки — блок «Быстрый демо-вход»: нажать **«👤 Студент (user@codeway.by)»**. Поля email/пароль заполнятся сами, затем выполняется обычный вход через `POST /api/v1/auth/login`.
3. Приложение откроет `/data`.

Что должно быть на экране: в шапке бейдж **«Студент»** и имя «Студент (Минск)»; меню: Главная, Данные, Логи, Файлы, Кабинет. Пункта **«👑 Админ-панель»** нет. В `/data` под заголовком «Данные» — счётчик записей, в таблице только записи студента (у части из них — источник «Excel Import»), чужих записей студента в списке нет.

---

## 2. Кабинет `/profile` (≈60 секунд)

1. Клик **«Кабинет»** в шапке (или `/profile`).
2. Показать карточку профиля слева: имя, email, бейдж роли **«Студент»**, курс, дата регистрации, ID.
3. Показать плитки справа: **📊 Записи** (с «+N за 7 дней · +N за 30 дней»), **📁 Файлы** (локально / GDrive), **⚡ Действия**, ниже — «Записи по статусу» с полосками.
4. Показать блок «Последние действия»: последние 10 операций **только текущего пользователя**, ссылка «весь журнал →» ведёт на `/logs`.
5. Изменить имя: в блоке «Редактирование профиля» вписать `Студент (Минск) — демо` и нажать **«Сохранить имя»**.

Что должно быть на экране: зелёная плашка «Имя обновлено», новое имя сразу появляется в карточке профиля и в шапке сайта. Ответ сервера — `PUT /api/v1/profile` (менять можно только `name` и `password`, `email`/`role` сервер отклоняет с 400).

Фразу для защиты: «Профиль и статистика считаются на сервере для владельца токена — студент не видит в кабинете ничьих цифр».

---

## 3. `/data`: создание, дублирование, импорт (≈90 секунд)

1. **Создание.** Кнопка **«+ Добавить запись»** → модальное окно «Добавление записи». Заполнить поля (Имя, Фамилия, Курс, Email, Статус) → **«Добавить»**.
   На экране: зелёное уведомление «Запись успешно добавлена (POST)», строка появилась в таблице, счётчик «Всего записей» +1.
2. **Дублирование.** В строке этой записи нажать кнопку **«⧉»** (tooltip «Дублировать»).
   На экране: уведомление «Запись продублирована», в таблице ещё одна такая же строка. Под капотом — `POST /api/v1/data/:id/duplicate`: сервер копирует только поля записи и заново ставит `id`, `ownerId`, `ownerName`, `createdAt` и `duplicatedFrom`.
3. **Импорт из Excel.** Кнопка **«📤 Импорт из Excel»** → в диалоге выбрать `students_sample.xlsx` из корня проекта (лист «Студенты_Беларусь», 12 строк, колонки Имя, Фамилия, Курс, Email, Телефон, Город, Статус, Стоимость).
   На экране: уведомление «Импорт из «students_sample.xlsx»: добавлено N, пропущено 0», таблица обновилась, появилась пагинация (записей стало больше 10). Под капотом — `POST /api/v1/data/import` с телом `{ items: [...] }`; владельцем всех строк сервер ставит текущего пользователя, `id`/`createdAt` генерирует сам, клиентские `id`/`ownerId` игнорируются.

Подсказка: у существующих записей колонок больше шести, а форма и таблица берут первые 6 колонок первой записи — поэтому в таблице могут отображаться поля «Имя, Фамилия, Курс, Email, Телефон, Город» без «Статус».

## 4. `/logs`: журнал студента (≈30 секунд)

1. Клик **«Логи»** в шапке.
2. Показать таблицу «История действий»: колонки Действие, Тип, ID объекта, **Пользователь**, Дата, «Сравнение» (кнопка 🔍 открывает окно сравнения «до/после» для CREATE/UPDATE/DELETE).

Что должно быть на экране: только действия студента — «Студент (Минск)» и строки вида «Создание / Данные» из предыдущих шагов. В правом верхнем углу **нет кнопки «Очистить логи»** — она рендерится только у администратора. Сервер отдаёт `GET /api/v1/logs` уже отфильтрованным по владельцу; прямой `DELETE /api/v1/logs` для студента вернёт 403 (см. шаг 6).

---

## 5. Вход админом (≈60 секунд)

1. Шапка → выпадающее меню пользователя → **«Выйти»** (сессия отзывается на сервере, `POST /auth/logout`).
2. `/login` → **«👑 Админ (admin@codeway.by)»**.
3. В шапке: бейдж **«Админ»**, имя «Администратор (Беларусь)», пункт **«👑 Админ-панель»**.
4. `/data` — теперь таблица содержит и записи студента (например, «Студент (Минск)» из шага 3), и записи администратора.
5. `/logs` — журнал целиком: действия и админа, и студента; появилась кнопка **«Очистить логи»**.
6. `/admin` — панель администратора: плитки «Пользователей / Записей / Файлов / Логов», таблица пользователей с ролями (👤 Пользователь, ✏️ Редактор, 🛡️ Модератор, 👑 Администратор), блок «Управление данными» с кнопками «Очистить все данные» и «Очистить логи».

> Очистку журнала лучше **показать, но не подтверждать** (или очистить в самом конце): после неё пропадут данные для показа «Последних действий» в кабинете.

## 6. Проверка «из-под капота»: права проверяет сервер (≈60 секунд)

Команды для PowerShell 7 (`pwsh`). Если используется встроенный Windows PowerShell 5.1, замените `-SkipHttpErrorCheck` на `try { … } catch { $_.Exception.Response; $_.ErrorDetails.Message }` либо просто откройте тот же URL в браузере DevTools — тело ответа приходит одно.

Получить токен студента через API:

```powershell
$login = Invoke-RestMethod -Method Post -Uri 'http://localhost:3001/api/v1/auth/login' -ContentType 'application/json' -Body '{"email":"user@codeway.by","password":"user123"}'
$studentToken = $login.token
($login | ConvertTo-Json)   # видно id, name, role, token
```

Для получения админского токена:

```powershell
$adminLogin = Invoke-RestMethod -Method Post -Uri 'http://localhost:3001/api/v1/auth/login' -ContentType 'application/json' -Body '{"email":"admin@codeway.by","password":"admin123"}'
$adminToken = $adminLogin.token
```

### 6.1 Студент видит только свои записи, админ — все

```powershell
# сколько записей видит студент и сколько — админ (X-Total-Count)
(Invoke-WebRequest -Uri 'http://localhost:3001/api/v1/data' -Headers @{Authorization="Bearer $studentToken"}).Headers['X-Total-Count']
(Invoke-WebRequest -Uri 'http://localhost:3001/api/v1/data' -Headers @{Authorization="Bearer $adminToken"}).Headers['X-Total-Count']
```

Ожидается: у студента — только его записи (id `1794989535478`, `1794989566008`, … и созданные в шаге 3), у админа — все.

### 6.2 Попытка удалить чужую запись студентом → 403

```powershell
# Найти id записей, которыми владеет админ (ownerId: 1)
$adminData = Invoke-RestMethod -Uri 'http://localhost:3001/api/v1/data' -Headers @{Authorization="Bearer $adminToken"} | Where-Object { $_.ownerId -eq 1 }
$foreignId = $adminData[0].id

# Студент пытается удалить чужую запись
$r = Invoke-WebRequest -Method Delete -Uri "http://localhost:3001/api/v1/data/$foreignId" -Headers @{Authorization="Bearer $studentToken"} -SkipHttpErrorCheck
$r.StatusCode      # 403
$r.Content         # {"error":"Можно удалять только свои записи"}
```

Та же операция с админским токеном — `200` и `{"success":true,...}` (лучше не выполнять, чтобы не удалять данные перед защитой; достаточно показать строку с 403).

> Записи `id` 1–3 в `db.json` сейчас записаны **без `ownerId`** — их привязывает к администратору миграция `migrateOwnership()` **при старте сервера**. Если сервер ещё ни разу не перезапускался после этого состояния файла, `$adminData` может быть пуст — тогда сначала выполните `npm run api` (или возьмите `id` из любой записи, которую админ видит в `/data`).

### 6.3 Поддельный токен не принимается → 401

```powershell
$r = Invoke-WebRequest -Uri 'http://localhost:3001/api/v1/data' -Headers @{Authorization="Bearer jwt_token_1_1700000000000_fakesignature"} -SkipHttpErrorCheck
$r.StatusCode      # 401
$r.Content         # {"error":"Требуется авторизация"}
```

Дополнительно — подделка владельца в теле запроса не работает:

```powershell
$body = '{"Имя":"Хакер","ownerId":1,"ownerName":"Администратор (Беларусь)"}'
Invoke-RestMethod -Method Post -Uri 'http://localhost:3001/api/v1/data' -ContentType 'application/json' -Headers @{Authorization="Bearer $studentToken"} -Body $body
# в ответе ownerId = 2 (id студента), а не 1 — сервер берёт владельца из токена
```

Почему это работает: формат токена `jwt_token_<userId>_<timestamp>_<подпись>`, подпись — HMAC-SHA256 с секретом `TOKEN_SECRET`; сервер пересчитывает её и сравнивает с постоянным временем (`timingSafeEqual`). Подделать `userId` без секрета нельзя, а при выходе токен отзывается и тоже даёт 401.

## Что говорить на защите

1. **Права проверяются на сервере, а не в браузере.** Каждый маршрут с данными закрыт middleware `requireAuth`, а админские — `requireAdmin`; интерфейс лишь не показывает кнопки, а решение принимает Express.
2. **Владелец записи берётся из подписанного токена, а не из тела запроса.** В `POST /data`, `/data/duplicate` и `/data/import` сервер сам ставит `ownerId` и `ownerName`, а присланные клиентом служебные поля отбрасываются.
3. **Токен подписан HMAC-SHA256 и проверяется при каждом запросе.** Подделку `userId` ловит проверка подписи с постоянным временем сравнения, а выход (`/auth/logout`) отзывает токен до перезапуска сервера.
4. **Список записей и журнал фильтруются на сервере хелпером `visibleTo`.** Студент физически не получает чужие записи и чужие логи в ответе API — их не видно даже в DevTools.
5. **Изменение и удаление проверяются хелпером `canTouch`.** Чужой `id` даёт 403 даже при ручном HTTP-запросе в обход интерфейса.
6. **Роль приходит из БД по токену, а не из localStorage.** Подмена `user.role` в браузере меняет только надписи и меню, но не права: сервер сверяет роль с записью пользователя в `db.json`.

## Ограничения текущей версии

- Токен — учебный аналог JWT, а пароли хранятся в `db.json` в открытом виде; для учебного проекта это допустимо, для реальной системы нужны bcrypt и настоящий JWT с TTL.
- Запись и корректная кодировка имён в PowerShell: `curl` — это alias на `Invoke-WebRequest`, поэтому в сценарии использованы нативные cmdlet'ы, а JSON-тела заданы одинарными кавычками (в PowerShell `"` внутри строки требуют экранирования `` ` ``).
- Если API недоступен, фронтенд переключается на `localStorage`-fallback; этот режим **не является проверкой прав**: без сервера любые данные видны только в своём браузере, а офлайн-сессия входит с ролью `user`. Демонстрацию прав проводить только при запущенном `npm run api`.
- Записи без `ownerId` видят только администраторы; старые записи при запуске сервера автоматически привязываются к первому администратору (`migrateOwnership`).
- Отзыв токена при выходе хранится только в памяти сервера: после перезапуска `npm run api` ранее отозванные токены снова принимаются (до истечения их собственного срока жизни), поэтому для демо используется постоянный `TOKEN_SECRET`, а не перезапуск сервера между опытами.
- Студент видит в `/logs` только строки, где `ownerId` совпадает с его `id`; старые логи, привязанные миграцией к администратору, ему не показываются — это ожидаемое поведение, а не ошибка.
